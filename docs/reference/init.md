# `vens init`

**Who this is for:** anyone who wants a valid `config.yaml` without writing one by hand.
**By the end of this page:** you know what `vens init` asks, what it writes, and when it refuses to overwrite.

For a walkthrough, see **[Quickstart](../getting-started/quickstart.md)**.

---

## Synopsis

```
vens init [--output FILE] [--force]
```

Ask a short series of questions about the system being scored and write the answers as a `config.yaml` that `vens generate` accepts. Only the project name and the three required context fields are mandatory; every other question can be skipped with Enter, except the three detection channels once you choose to declare detection.

---

## What it asks

| Question | Required | Values |
|---|---|---|
| Project name | Yes | Any non-empty string |
| Project description | No | Free text |
| Exposure | Yes | `internal` / `private` / `internet` |
| Data sensitivity | Yes | `low` / `medium` / `high` / `critical` |
| Business criticality | Yes | `low` / `medium` / `high` / `critical` |
| Availability requirement | No | `low` / `medium` / `high` / `critical` |
| Compliance requirements | No | Comma-separated list, e.g. `GDPR, SOC2` |
| Traceability | No | `none` / `per_request` / `per_individual` |
| Listener | No | `present` / `absent` / `unknown` |
| Data subjects | No | `none` / `one_individual` / `hundreds` / `thousands` / `millions` |
| Declare detection | No | `y` / `n`; after `y`, the network, host and application channels are each required |
| Security controls | No | `y` / `n` for each of `waf`, `ddos_protection`, `segmentation`, `zero_trust`, `antivirus` |
| Notes | No | Free text |

Before business criticality, the wizard prints what the field declares and, for each value, its meaning and the worst Financial damage and Reputation damage it declares; before traceability, listener, data subjects and detection, what the field and each value mean. Both are in the words of the **[config.yaml reference](config-schema.md)**; each control is asked with its scope. An invalid answer is re-prompted instead of failing. The generated file starts with `schema_version: 2` and is validated before it is written: `vens init` parses the final file (header included) and refuses to write a config `vens generate` would reject.

Traceability, data subjects or detection skipped with Enter is left out of the file. `vens generate` then warns at load and uses that field's fallback, and `--strict` refuses the file: see **[Load errors and warnings](config-schema.md#load-errors)**.

---

## Flags

| Flag | Default | Description |
|---|---|---|
| `--output`, `-o` | `config.yaml` | Path of the config file to write. |
| `--force` | `false` | Overwrite the output file if it already exists. |

---

## Existing files

An existing file is left alone unless `--force` is passed. The check happens twice: once before the first question, which refuses an existing file without `--force` before you answer anything, and again at write time — a file created while the user was answering is not silently replaced. A directory as the target, an empty `--output`, or a missing parent directory also fails before any question is asked. Any other write error, such as a read-only directory, shows only at the end, when the file is written.

The generated file starts with a comment telling you how to use it:

```yaml
# Generated by `vens init`. Edit any value, then pass this file to vens generate --config-file (see vens generate --help).
```

Edit any value in place — the file is a normal `config.yaml`. The wizard does not ask `audit_requirement` or the `ids`, `siem` and `edr` controls, which move no score; it asks traceability and detection instead. Every field and its values are in the **[config.yaml reference](config-schema.md)**, and **[Describe your system context](../guides/configuration.md)** explains how to choose them.

## Example

```bash
$ vens init
Project name: my-api
Project description (optional, Enter to skip): Backend API
Exposure [internal/private/internet]: internet
Data sensitivity [low/medium/high/critical]: high

Business criticality: Choosing a value declares the worst an exploit of this service could cost the business, as OWASP's Financial damage and Reputation damage, with a low, a medium and a high technical impact: the highest of the CVE's Loss of confidentiality, integrity and availability, low under 3, medium from 3 to under 6, high from 6, and high with no usable CVSS v3 vector. vens sets both factors from it; no question asks them. With a high technical impact it is your worst case; the steps down to medium and low are vens's customization of OWASP's options, not calibrated against experts' ratings, in the direction OWASP gives: the business impact stems from the technical impact.
  low: Dev / test / sandbox. With a high technical impact, less than the cost to fix the vulnerability (FD 1) and minimal damage (RD 1); medium, less than the cost to fix the vulnerability (1) and minimal damage (1); low, less than the cost to fix the vulnerability (1) and minimal damage (1).
  medium: Internal tools. With a high technical impact, a minor effect on annual profit (FD 3) and loss of major accounts (RD 4); medium, less than the cost to fix the vulnerability (1) and minimal damage (1); low, less than the cost to fix the vulnerability (1) and minimal damage (1).
  high: Customer-facing, important operations. With a high technical impact, a significant effect on annual profit (FD 7) and loss of goodwill (RD 5); medium, a minor effect on annual profit (3) and loss of major accounts (4); low, less than the cost to fix the vulnerability (1) and minimal damage (1).
  critical: Revenue-critical. With a high technical impact, bankruptcy (FD 9) and brand damage (RD 9); medium, a significant effect on annual profit (7) and loss of goodwill (5); low, a minor effect on annual profit (3) and loss of major accounts (4).
Business criticality [low/medium/high/critical]: critical
Availability requirement (optional) [low/medium/high/critical]: high
Compliance requirements, comma-separated (optional) [PCI-DSS, HIPAA, GDPR, SOX, ISO27001, FedRAMP, NIST, CCPA, SOC2, FISMA, ITAR, CMMC]: GDPR

Traceability: What is in place, not what is required. Records kept in front of the service count when they cover every request to it (a gateway or proxy log). The value declared must hold across the whole service: where only part of it records this, declare the weaker value.
  none: nothing records the requests the service receives or who made them
  per_request: each request is recorded with its time and origin (source address, client), not with the individual who made it
  per_individual: as per_request, and each action of an authenticated user is recorded with that user's identity
Traceability (optional) [none/per_request/per_individual]: per_request

Listener: Does this deployment accept connections others open?
  present: this deployment accepts connections that other parties open: it listens on a port or socket, as a server or as a peer others connect to
  absent: it accepts none: no listening port or socket, such as a batch job, a command-line tool, or a client that only opens connections
  unknown: not stated
Listener (optional) [present/absent/unknown]: present

Data subjects: How many distinct people's personal data this service can read: what it stores, what passes through it, and what it can fetch with its own access. A count belongs to the band whose interval holds it, and a count of 2 to 99 belongs to hundreds. Nothing is inferred from data_sensitivity.
  none: 0
  one_individual: 1
  hundreds: 2 to 999
  thousands: 1,000 to 999,999
  millions: 1,000,000 or more
Data subjects (optional) [none/one_individual/hundreds/thousands/millions]: thousands

Detection: Declaring a channel's level states it for every instance of this service. Where only part of the service is covered, the level declared is the one that holds for all of it.
Declare detection [y/N]: y

Channels:
  network: each attempt crossing the network to or from the service is recorded where it can be seen
  host: process, file and privilege activity on the hosts that run the service is recorded
  application: the service's own logs record each request or action an attempt would make

Levels:
  not_logged: nothing is recorded
  logged: recorded, and nobody reviews it
  logged_and_reviewed: recorded and reviewed, by people or by alerts that people act on
  active_in_application (application only): the service itself detects attacks and acts on them
Detection, network [not_logged/logged/logged_and_reviewed]: logged
Detection, host [not_logged/logged/logged_and_reviewed]: not_logged
Detection, application [not_logged/logged/logged_and_reviewed/active_in_application]: logged_and_reviewed

Security controls in operation for this deployment:
waf: Web Application Firewall. Scope: SQL injection, XSS, path traversal [y/N]: y
ddos_protection: DDoS mitigation (CloudFlare, AWS Shield…). Scope: Availability / DoS CVEs [y/N]: n
segmentation: Network micro-segmentation. Scope: Lateral movement [y/N]: n
zero_trust: Zero-trust architecture. Scope: Authentication bypass, lateral movement [y/N]: n
antivirus: Traditional AV / anti-malware. Scope: Known malware signatures [y/N]: n
Notes (optional, Enter to skip):
Wrote config.yaml
```
